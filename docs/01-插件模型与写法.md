# 01 · 插件模型与写法

## 1. 插件是什么

DSH 由 Cordis 驱动，产品里没有特权内核。模型适配器、工具注册表、会话日志，以及 agent 主循环本身，都是插件，因此每一部分都能从配置层替换。

官方对 Cordis 的归纳是五个概念：

| 概念 | 含义 |
|---|---|
| **插件** | 实现 Service 的对象。可以是带 `apply(ctx)` 的函数、带 `inject` 的对象，或 `Service` 子类 |
| **上下文** | 服务的容器。一个服务占据稳定的 `ctx.<key>`（如 `ctx.tools`、`ctx.llm`、`ctx.sessions`）。插件通过 key 查找服务，不 import 具体实现 |
| **inject** | 声明服务依赖。插件等这些服务就绪才启动，加载顺序由依赖表达，不靠手工编排 |
| **类型化事件** | 服务用 TypeScript 声明合并注册事件名，以 `emit` / `waterfall` / `parallel` / `serial` / `bail` 分发 |
| **可逆注册** | 提示词片段、工具 schema、适配器、监听器都通过 `ctx.effect()` 或 `ctx.on()` 安装，reload 和 teardown 时按预期撤销 |

> 来源：官方 [docs/cordis-primer.zh.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.zh.md)、[deepseek.com/harness](https://www.deepseek.com/harness/en/)

## 2. 三种插件形态

官方 `develop/basic` 给出三种写法。**函数形式足够覆盖大多数场景**；只有需要向其他插件提供服务时才用类形式。

### 2.1 函数形式（默认选择）

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  // 必需依赖在 apply 运行前就已就绪
  console.log('[hello-plugin] plugin loaded!')
}
```

### 2.2 对象形式

```ts
import type { Context } from '@deepseek-ai/cordis'

export default {
  name: 'my-plugin',
  inject: ['tools'],
  apply(ctx: Context) {
    // ...
  },
}
```

### 2.3 类形式（对外提供服务）

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

export default class MyService extends Service {
  static inject = ['tools']

  constructor(ctx: Context) {
    super(ctx, 'myService')   // 'myService' 就是服务名，消费方用 ctx.myService 访问
    // 同步初始化放在构造函数里
  }
}
```

配套的类型声明合并，让 `ctx.myService` 有正确类型：

```ts
declare module '@deepseek-ai/cordis' {
  interface Context {
    metrics: MetricsService
  }
}
```

> 来源：官方 `develop/basic/`、`develop/framework/service`

## 3. 四个导出的分工

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

/** 诊断用显示名 */
export const name = 'my-plugin'

/** 声明必需服务；Loader 等它们就绪再执行 apply */
export const inject = ['tools']

/** 部署期配置的校验 schema */
export interface Config {
  greeting: string
  maxRetries: number
}
export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  maxRetries: Schema.number().default(3),
})

/** 插件主体：注册贡献，且每一项都注册为可逆 effect */
export function apply(ctx: Context, config: Config) {
  console.log(config.greeting)
}
```

`apply` 的签名随 `Config` 是否存在而变：有 `Config` 导出时是 `(ctx, config)`，没有时是 `(ctx)`。

**必需依赖与可选依赖的区别**：

```ts
// 必需：服务缺席时插件不加载
export const inject = ['tools']

// 可选：不写 inject，在使用处用 ctx.get() 查询
export function apply(ctx: Context) {
  const metrics = ctx.get('metrics')
  metrics?.record('plugin_loaded', 1)
}
```

不要在可选依赖上使用属性代理，那是拓扑敏感的。

## 4. 工具插件

工具注册在 `ctx.tools` 上，schema 会自动流入系统提示词组装。

```ts
import { readFile } from 'node:fs/promises'
import type { Context } from '@deepseek-ai/cordis'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'my-tool'
export const inject = ['tools']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({
    name: 'read_file',
    description: 'Read a file from disk.',        // 模型看到的能力描述
    parameters: {
      path: { type: 'string', required: true, description: 'Absolute path' },
      limit: { type: 'number' },                   // 默认可选
    },
    output: {
      schema: { type: 'string' },
      render: (_args, value) => [{ type: 'text', text: value }],
    },
    async execute(args, exec) {
      // args 已按 schema 校验并推导类型：{ path: string; limit?: number }
      return readFile(args.path, { encoding: 'utf8', signal: exec.signal })
    },
  }))
}
```

`ctx.tools.register()` 也直接接受原始 JSON Schema 的 `ToolDefinition`，MCP 来源的工具就是这样到达的。`defineTool` 是第一方工具用的类型化辅助函数。

### 4.1 execute 契约的硬规则

来自官方 [docs/cookbook/adding-a-tool.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cookbook/adding-a-tool.md)：

| 规则 | 说明 |
|---|---|
| **参数自动校验** | `defineTool` 在 `execute` 前校验 types、required、字面量约束、exact-one union、嵌套值。但 DSL 表达不了的约束（非空字符串、正数、跨字段规则）仍需自己检查。直接注册原始 JSON Schema 的工具，输入校验自己负责 |
| **注册借用只读定义** | 注册后不要改 schema 或替换回调。要热换工具，就释放它所属的 effect 再注册替代品 |
| **执行身份受保护** | `callId`、`name`、`arguments`、`agent`、`token`、`signal`、可选的 `parent` 在分发全程不可变。把 `args` 当只读输入 |
| **只返回一个规范 JSON 值** | `output.schema` 用 `ValueSchemaSpec`，根可以是 object / array / scalar / null。不要返回内容块，也不要让调用方从散文里解析 id 和字段 |
| **抛出或返回非法值 = isError** | 基础设施故障就抛。成功的领域结果（比如非零退出码）要放进规范值里返回 |
| **遵守 `exec.signal`** | 信号触发时取消进行中的工作 |
| **后台长任务走 `ctx.jobs.start()`** | 见 4.3 |

### 4.2 UI 卡片与模型内容分开

`output.render` 决定模型看到什么；UI 卡片由 `presentCall` / `presentResult` 返回的 `card` 渲染意图决定，两者是独立设计。

```ts
// 调用态卡片（PENDING）
{ card: 'generic',  title, kind?, rawInput?, content?, locations? }
{ card: 'terminal', title, description?, cwd? }      // 你的调用就是 shell 命令
{ card: 'diff',     title, diffs, locations? }       // 创建/修改文件

// 结果态卡片（presentResult）
// generic / terminal / diff / read / search / web 各自有约定的字段
```

**两条硬规则**（违反会咬人）：

- **纯函数**。这些呈现函数在实时流式输出和会话日志 REPLAY 时都会跑，所以必须是 `args`（加结果）的纯函数：没有 I/O，不读会话状态，不用时钟和随机数。想在 `presentCall` 里拿文件的旧内容或当前工作目录，就是走错方向了，那属于持久结果元数据或适配器。
- **UI 专用格式不进模型结果**。` ```console ` 围栏、diff、相对化路径，都不该为了服务 UI 而写进规范值或模型内容。

### 4.3 后台长任务

由部署配置开关 `run_in_background`，然后通过 `ctx.jobs.start()` 注册：

```ts
ctx.jobs.start({ kind, label, owner: exec.agent, run })
```

成功后返回带 `jobId` 的类型化句柄。`job_kill`、owner 释放和服务 teardown 负责它的生命周期。一旦 `ctx.jobs.start()` 发布了 id，就用任务自己的取消信号，而不是 `exec.signal`。

### 4.4 执行策略与观察

**不要把部署策略写进工具里**，用扩展点：

| 需求 | 扩展点 |
|---|---|
| 允许 / 拒绝 / 询问策略 | `tools/pre-execute`（waterfall，返回类型化决策） |
| 不可撤销的最终拒绝 | `ctx.tools.guard()` |
| 包裹分发（超时 / 重试 / 指标） | `tools/execute`（只有 `exec.signal` 可替换） |
| 替换呈现内容或返回值、附加模型可见上下文 | `tools/post-execute` |
| 只观察不可变的规范化结果 | `tools/result` |

## 5. 配置（Config）

用 `@deepseek-ai/schemastery` 定义，类型和运行时校验合一：

```ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export interface Config {
  apiKey: string
  timeout: number
  mode: 'fast' | 'accurate'
}

export const Config = Schema.object({
  apiKey: Schema.string().required(),
  timeout: Schema.number().default(30000),
  mode: Schema.union(['fast', 'accurate']).default('fast'),
})

export function apply(ctx: Context, config: Config) {
  // config 已校验，类型安全
}
```

装配时在 `cordis.yml` 传值：

```yaml
- insert:
    - id: hello
      name: './src/my-plugin.ts'
      config:
        greeting: 'Hi there'
        maxRetries: 5
```

### 5.1 两条设计原则

**无硬编码可调参数。** Harness 的约定是：凡是不同部署可能需要不同值的参数，都必须定义为配置字段。检验标准是一句话：能不能在 `cordis.yml` 里改变这个值，而不需要修改代码？

```ts
// 错：写死超时
const TIMEOUT = 30000

// 对：可配置
export interface Config {
  timeoutMs: number   // 默认 30000
}
```

**配置错误要响亮。** 在 schema 里表达自身完备的约束，让无效配置在插件加载时失败。

### 5.2 两个容易踩的细节

- **不要导出普通对象当 `Config`**，它不满足 Cordis 要求的 Standard Schema 接口。
- **`!!js` 只能出现在插件的 `config` 和条目的 `disabled` 下**，其他 metadata 保持字面量。需要按环境选插件时用 overlay，不要用 `!!js`。

配置变更会触发插件热替换：框架卸载旧实例、加载新实例。因为注册都是 effect 并会自动清理，替换后不会保留旧实例的注册。

## 6. 事件系统

事件是插件间通信的核心机制，也是 DSH 的主要扩展点。

### 6.1 五种分发模式

| 模式 | 是否 await | 顺序 | 有返回值 |
|---|---|---|---|
| `emit` | 否 | 监听器按注册顺序观察 | 否 |
| `waterfall` | 否 | 监听器按注册顺序观察 | 是 |
| `parallel` | 是 | 所有监听器并行观察 | 否 |
| `serial` | 是 | 监听器按注册顺序观察 | 是 |
| `bail` | 否 | 按注册顺序，直到某个监听器返回 bail 值 | 是 |

分发模式是事件公开约定的一部分，不能随便换。

### 6.2 waterfall 必须调用 next()

`ctx.waterfall` 是环绕中间件。监听器接收 `(...args, next)`。

```ts
ctx.on('tools/pre-execute', async (exec, next) => {
  if (!(await isAllowed(exec))) {
    return { kind: 'deny', reason: 'Denied by policy.' }  // 短路，这是设计意图
  }
  return next()                                            // 委托给下游
})
```

**不调用 `next()` 直接返回就会短路整条链。** 对单决策事件这是设计意图（策略监听器拥有决策权时不委托）；只做标注或观察的监听器必须委托。

只有必须在普通注册之前运行时才用 `prepend: true`。

### 6.3 类型安全

用 TypeScript 声明合并注册事件名：

```ts
import '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Events {
    'my-plugin/ready': (payload: { id: string }) => void
    'my-plugin/check': (input: string) => boolean | undefined
    'my-plugin/transform': (input: string, next: () => Promise<string>) => Promise<string>
  }
}
```

此后 `ctx.on` 和 `ctx.emit` 都会正确推导类型。

### 6.4 事件命名与两类事件

Harness 的 Cordis 事件遵循 `namespace/action` 命名，例如 `agent/pre-step`、`agent/request`、`tools/result`、`session/event`。

**要区分两类事件**：

- **持久会话事件**：`turn/*`、`step/*`、`system/message`、`user/message`、`assistant/*`、`tool/*`。追加进会话日志，重启后仍可重建。
- **实时扩展点**：`agent/*`、`tools/*`、`fs/*`、`telemetry/*`。只做运行期协调。

`turn/*`、`step/*`、`tool/call`、`tool/result`、`compaction/*` 是持久化的会话事件类型，**不是同名 Cordis 事件**。要观察它们，监听 `session/event` 并检查 `event.type`。

**模型可见即已记录。** 抵达模型请求的一切都必须能从日志重建，并有运行时不变量断言这一点。要给模型加新的可见输入，就扩展 `SessionEventMap` 并增加一个会话事件，而不是绕过日志。

### 6.5 挑扩展点的速查

| 目标 | 机制 |
|---|---|
| 允许 / 拒绝 / 询问工具调用 | `tools/pre-execute` |
| 包裹工具执行生命周期 | `tools/execute` |
| 改写工具结果或呈现内容 | `tools/post-execute` |
| 只观察最终结果 | `tools/result` |
| 改写 / 拒绝进入 step 的消息 | `agent/pre-step`（waterfall） |
| 改写模型请求配置 | `agent/request`（waterfall） |
| 收尾 turn / 强制再走一步 | `agent/turn-stopping`（serial，无 `next()`） |
| 添加模型可见上下文 | `agent.inject()`，落到下一次获准的请求 |
| 添加模型提供方 | 在 `ctx.llm` 注册适配器 |
| 添加用户命令 | 在 `ctx.commands` 注册，无需模型轮次即可分派 |
| 添加后台工作 | 在 `ctx.jobs` 注册 |

完整映射见官方 [docs/architecture.zh.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.zh.md) 的「新行为的归属位置」一节。

## 7. 生命周期

### 7.1 Fiber 状态机

每个被加载的插件拥有一个 Fiber 作用域：

```
PENDING → LOADING → ACTIVE
                 ↘ FAILED
ACTIVE → UNLOADING → DISPOSED
```

| 状态 | 含义 |
|---|---|
| PENDING | 已声明，依赖未就绪 |
| LOADING | 依赖就绪，正在执行 `apply` |
| ACTIVE | 运行中 |
| FAILED | `apply` 抛出异常 |
| UNLOADING | 正在卸载并释放资源 |
| DISPOSED | 已完全卸载 |

### 7.2 依赖驱动的加载与卸载

声明了 `inject` 的插件会等所有必需服务就绪。**如果依赖的服务在运行期消失（例如提供方被替换），插件会自动 dispose；服务恢复后自动重新加载。** 这防止插件调用已不存在的服务。

### 7.3 自动清理

以下操作都会被自动追踪和清理：

- `ctx.on(event, handler)` — 事件监听
- `ctx.tools.register(tool)` — 工具注册
- `ctx.llm.registerAdapter(names, adapter)` — LLM 适配器注册
- `ctx.effect(() => cleanup)` — 自定义资源

```ts
export function apply(ctx: Context) {
  // 有需要手动清理的资源时，用 ctx.effect 告诉框架怎么清理
  ctx.effect(() => {
    const connection = createConnection()
    return () => connection.close()   // 插件卸载时运行
  })
}
```

**清理顺序有个坑**：插件卸载时，处置器按注册顺序的**逆序**开始调用，但多个异步处置器会**并发执行**，不保证逐个完成。有顺序依赖的清理步骤必须放进同一个 `ctx.effect()` 返回的处置器里，由它负责串行等待。

### 7.4 子 Fiber

`ctx.plugin()` 创建子 Fiber，继承父上下文但有独立生命周期；父插件卸载时子插件一起卸载。

手动提前终止：

```ts
const fiber = ctx.plugin(myPlugin)
await fiber.dispose()
```

`dispose` 保证：该插件拥有的所有注册被移除；子插件递归卸载；返回的 Promise 在所有异步清理完成后兑现。

### 7.5 HMR

通过 `cordis.yml` 加载 `@deepseek-ai/cordis-plugin-hmr` 后，修改插件源文件会触发卸载旧插件、重新加载新代码、执行新的 `apply`。

因为注册会被自动清理，热替换不会保留旧实例的注册。**前提是你的注册确实走的是 `ctx.effect()` / `ctx.on()` 系**，在 `apply` 里裸干的副作用不会被回滚。
