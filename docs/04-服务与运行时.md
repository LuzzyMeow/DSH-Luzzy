# 04 · 服务与运行时

前三篇回答的是「插件怎么写」（01）、「怎么组装与安装」（02）、「哪里会咬人」（03）。
这一篇换方向：插件跑起来之后**能调用哪些服务**，以及一次模型调用从进到出走过了什么。

来源与前三篇同一套规矩。新增的证据形态是官方**生成的 Cordis API 目录**，即每个子系统页末尾那一段：签名与源码等价，由 `pnpm run verify-cordis-catalog` 检查漂移。凡是本页给出签名的，出处一律落到 `packages/.../src/index.ts`。

## 2. 系统提示词

01 §1 只写了「提示词片段通过 `ctx.effect()` 安装」，01 §4 写了「schema 会自动流入提示词组装」。组装本身没展开过。

### 2.1 段落与运行时上下文

`ctx.systemPrompt` 提供两套注册原语。段落进系统提示词，运行时上下文以持久的 user-role 快照落地。

```ts
ctx.systemPrompt.section({
  name: 'my-plugin/instructions',
  order: 1000,
  text: 'Always answer in the user\'s language.',
})
```

`PromptSection` 的字段：`name`（唯一，重名抛错）、`order`（升序串联，order 相同则按名称的代码单元序）、`text`（静态字符串，或每次组装时求值的 provider）、`interpolate`（默认 true，`{{variable}}` 会被替换）、`complete`（声明这是完整提示词，组装仍跑协作式 waterfall，之后把这一段还原为唯一段落；多个 effective `complete` 会让组装失败）。

`order` 就是视频里说的那个参数：**升序排列，数字越大越靠后**。仓库贡献方不自己编数字，用 `getSectionOrder(name)` 解析中心持有的具名分配；运行时上下文用 `getContextOrder(name)`。

### 2.2 组装接口全貌

```ts
section(section: PromptSection): () => void
context(context: PromptContext): () => void
variable(name: string, provider: (context: AssembleContext) => string | undefined): () => void
tools(provider: (context: AssembleContext) => ToolProviderResult): () => void
suppressRuntimeContext(): () => void
getSectionOrder(name: PromptSectionOrderName): number
getContextOrder(name: PromptContextOrderName): number
async assemble(context?: AssembleContext): Promise<PromptAssembly>
```

`assemble()` 先串全球与作用域提供方、剥离工具参数、应用规范排序，再跑 `system-prompt/assemble` waterfall。作用域内的段落和变量会遮蔽全局同名项。waterfall 的返回值是权威结果，唯一例外是 effective `complete` 段落会在之后被还原。

事件两个：`system-prompt/assemble`（waterfall，专家级，作用域过滤）、`system-prompt/change`（emit，无过滤，全局变更影响每个作用域）。

### 2.3 提示词不是请求字段

这条容易猜错。渲染后的系统提示词**不作为请求字段发给模型**，它被提交为 surface 第 0 号节点上的 `system/message` 事件，作为派生历史里的消息到达模型。所以提示词变更表现为替换或追加一个系统节点，请求头保持不变。

首次接纳的步骤会在用户消息之前预留系统头节点，即使提示词为空。

> 来源：`docs/subsystems/system-prompt.zh.md`（含 `PromptSection` / `PromptContext` / `SystemPrompt` 生成签名）；`docs/subsystems/session.zh.md` 关于 `EpochHeader` 的段落。

## 3. 会话与上下文重建

01 §6.4 提过一句「模型可见即已记录」，但没讲机制。这是 DSH 最容易被误解的一处。

### 3.1 仅追加日志是唯一真源

`Session` 是一份由类型化 `SessionEvent` 组成的**仅追加日志**，是 agent 完整交互历史的唯一真源。**LLM 消息历史从日志派生，从不单独存储**；回放就是从同一组事件重新派生。

请求信封（`EpochHeader`：调用配置 + 适配器提供默认值的标记 + 已组装的工具 schema）也写入日志，因此每个请求都是日志的纯函数。

### 3.2 `deriveMessages()`

```ts
append<T extends SessionEventType>(
  type: T,
  data: SessionEventMap[T],
  ...opts: T extends SurfaceEventType ? [opts: SurfaceIntent<T>] : []
): SessionEvent<T>

deriveMessages(): Message[]
deriveEventMessage(event: SessionEvent): Message | null
```

`deriveMessages()` 走 surface 的顺序序列，把日志投影成模型看到的 `Message[]`。两条性质值得记住：

- **缓存**：纯尾部增长只花 O(新节点)；发生替换或消息投影时才重建。
- **冻结**：每次调用返回新数组，但里面的 `Message` 对象是共享且深冻结的。**通过投影改已记录的历史在类型上不可表达。**

`deriveEventMessage(event)` 是折叠逐节点用的纯函数，公开暴露给外部重建器，让它们能以完全相同的规则投影日志前缀，不与缓存分歧。插件要改现有消息内容，注册纯消息投影（`ctx.sessions.registerMessageProjection()`）。

### 3.3 `ctx.sessions` 的调用面

```ts
create(id?: SessionId, options?: CreateSessionOptions): Session
prepare(id?: SessionId, options?: PrepareSessionOptions): Session
enter(session: Session): () => void
announce(session: Session): void
async flush(session: Session): Promise<boolean>
get(id: SessionId): Session | undefined
list(): Session[]
fork(source: SessionForkSource, boundary?: SessionSeq, childSessionId?: SessionId): Session
registerMessageProjection(projection: SessionMessageProjection): () => Promise<void>
```

别用单个 `create()` 就算完。`prepare` → `enter` → `announce` 是给**需要按序拆卸**的场景准备的：agent 工厂把会话生命周期折进自己那一个 `ctx.effect`，卸载时会话和 agent 作为一条有序链一起拆，而不是两个赛跑的兄弟 effect，后者会在驱动器的收尾事件提交之前就摘掉发布钩子。

`flush(session)` 是持久化检查点的入口。store 持有 carrier，所以调用方必须走这里，不能自己派发裸 `ctx.parallel('session/flush', …)`。

会话事件四个：`session/created`（emit，同步抛错可否决并回滚）、`session/disposed`（emit）、`session/event`（emit，提交后 fire-and-forget 的追加入口，观察者失败被包含，不会让已提交的追加失败）、`session/flush`（parallel，await 全部监听器，无 waterfall 否决）。

### 3.4 持久化不在 store 里

`ctx.sessions` 是**内存** store，它故意不实现持久化。agent 生命周期给每个已发布会话的写句柄挂一个日志写入器；**在生命周期之外发布的会话什么也不持久化**。后端、世代选择、崩溃恢复是 [persistence](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.zh.md) 的事。

> 来源：`docs/subsystems/session.zh.md`（`Session` 类与 `ctx.sessions` 的生成签名）；`docs/architecture.zh.md`「会话日志」一节。

## 4. 模型调用

01 §7.3 只出现过 `ctx.llm.registerAdapter()`。调用侧没写。

```ts
registerAdapter(providers: string[], adapter: LlmAdapter): AdapterRegistrationHandle
async prepareCall(config: LlmCallConfig, signal?: AbortSignal): Promise<PreparedLlmCall>
stream(options: GenerateOptions): AsyncIterable<StreamChunk>
```

`prepareCall()` 返回的是一次性句柄，它在**头日志记录与派发之间保住那次注册**，所以 HMR 换掉适配器时，不会把一个适配器的能力结果和另一个适配器的派发拼在一起。要日志与流式共享同一次注册，就得走 `prepareCall`，`resolveCallConfig()` 那个独立查询绑不住后续派发。

`stream()` 返回原始 chunk 流（token 级增量）。适配器选择、派发与迭代失败会变成终结性的 `error` 或 `aborted` finish chunk；中间件、嵌套调用、清理与消费方失败则照常抛出。

事件 `llm/stream` 是 waterfall，包住每一次流式模型调用，重试、重放、路由都能挂在这里。call `next()` 到达适配器的流，或者直接 yield 自己的 chunk 短路。注意 loop 构造的请求带进程本地的 `markAgentLoopRequest` 身份且**到达时已深冻结（改它会抛）**。它的内容是会话日志的纯函数，监听器只读，不改写。

> 来源：`docs/subsystems/llm-streaming.zh.md` 生成的 Cordis API 小节。

## 5. shell 与后台任务

### 5.1 `resolve` / `run` / `start` 三分

```ts
resolve(request: ShellExecRequest): ShellExecSpec     // 应用实现自有的默认值与上限
run(spec: ShellExecSpec): Promise<ShellRunResult>      // 前台
start(spec: ShellExecSpec): Promise<ShellProcess>      // 后台，异步准备完成后发布句柄
```

这个 seam 把**面向模型/插件的请求**（`workdir` / `timeoutMs` / `stdoutMaxBytes` 都可选）与执行器实际使用的**完全解析后的 spec**（这些字段必填）分开。工具层在两者之间调一次 `resolve()`。这就是 `ctx.shell.resolve` 的作用：补全工作目录、超时，并把值夹到实现的上限内。

`run()` 只在基础设施故障时 reject。非零退出、超时终止、中止终止都**带描述性结果 resolve**。`ShellRunResult` 把 `timedOut`、`aborted`、`signal`、`exitCode` 分成四个独立字段：一个进程可以既超时又以退出码 0 退出（它捕获了信号），所以调用方不会把被提前中断的运行误读成正常成功。

`start()` 返回的句柄**没有 id，也没有 owner**。`readOutput()` 是增量的：连续读不会重复投递；丢数据的读会置 `lossy` 并指向完整流的 spill 文件。

`stdin` 和 `env` 是受信任的进程内插件输入，不建模给模型。面向模型的 bash 工具要用 stdin 就用 heredoc 或管道。`stdoutMaxBytes` 同样只给受信任插件用，让前台消费方在有界预算内取完整 stdout，不改 stderr、后台任务或工具的常规上限。

### 5.2 后台：`shell.start` 与 `ctx.jobs` 是两层

```ts
ctx.jobs.start(spec: JobStart): JobId
ctx.jobs.list(caller?: Agent): JobSnapshot[]
ctx.jobs.get(id: JobId, caller?: Agent): JobSnapshot
ctx.jobs.read(id: JobId, caller?: Agent): JobRead
ctx.jobs.kill(id: JobId, caller?: Agent, reason?: string): 'requested' | 'already-finished'
ctx.jobs.wait(id: JobId, timeoutMs: number, caller?: Agent, signal?: AbortSignal): Promise<JobSnapshot>
ctx.jobs.onJobDone(listener: JobDoneListener): () => void
ctx.jobs.onJobsChanged(listener: JobsChangedListener): () => void
ctx.jobs.attachController(name: string): () => void
```

`ctx.shell` 返回进程句柄，**不注册后台任务**。把它接进通用任务运行时的是 `dsh-tool-bash`：它把句柄适配成 `ctx.jobs.start()` 的钩子，此后由 jobs 运行时拥有任务标识与生命周期。所以两个 API 不是二选一，是上下两层。

`ctx.jobs` 的语义里有两条硬约束：注册活得比 producer 和 controller fiber 长；`start` 在没有已附加的 controller 服务该 spec 的 owner 时**拒绝开工**：producer 不能启动一个 owner 收不到也停不了的任务。任务 id 可预测，所以边界靠授权而不是保密（按 owner 的 session id 隔离）。

### 5.3 换 provider 就到沙箱

本地执行器通过 `ctx.subprocess` spawn 进程；沙箱化执行器用 `ctx.sandbox` 包装 argv，并通过 `ctx.shell.sandboxMode` 暴露配置的模式回退值。工具层向 `ctx.sandboxPolicy` 要为每个调用会话把持久 `sandbox/mode` 覆盖值与不可变 cwd 解析成 `ShellExecRequest.sandboxPolicy`。

调用方只看 `ctx.shell`。换后端就是换提供方，面向模型的 bash 工具一行不用改。这条链的理由见 §7。

> 来源：`docs/subsystems/shell.zh.md`、`docs/subsystems/jobs.zh.md`、`docs/architecture.zh.md`「能力 seam」与「新行为的归属位置」。

## 6. 一次轮次的骨架

01 §6.5 那张表回答「想做某件事挂哪个扩展点」。这张回答「不挂任何东西时，一次对话默认怎么走」。

### 6.1 定义

一个**步骤**是一次模型请求加上它调用的工具。一个**轮次**包含零个或多个步骤：它在领取首条输入之前打开，在不再欠下任何工作时关闭。

### 6.2 流程

以下是官方 `architecture.zh.md` 给出的完整骨架，原样引用：

```text
turn/start
  claim next-step input plus one queued message
  assemble prompt sections + tool schemas; project runtime context
  -> agent/pre-step                   reject | enter(messages, startsRequestSeries?)
     reject, or a first enter rewritten empty -> close the turn with no step
     step/start
     agent/request -> prepareCall (cancellation commits neither system nor users)
     reconcile system/message using the prepared call capability
     append entered messages as user/message; log request/header and request/context as needed
     derive and freeze model history from the log
     stream the bound prepared call -> llm/stream -> agent/assistant-stream start
       agent/assistant-stream chunk*
       assistant/message | assistant/attempt -> agent/assistant-stream end
     tool/call* -> tools/pre-execute -> tools/execute -> tools/post-execute -> tool/result*
     step/end
     tools owe another request, or next-step input arrived -> claim -> next step
  -> agent/turn-stopping
turn/end
```

对照 §3 读这串流程会清楚很多：`system/message` 和 `user/message` 是**写进日志**，`derive and freeze model history` 就是 `deriveMessages()`，请求不是攒出来的，是从日志投影出来的。

### 6.3 两类事件：一条动作写两处

流程里每个动作都在两个地方留痕，用途不同。这个分工在 01 §6.4 只分了一半。

| | 持久会话事件 | 实时扩展点 |
|---|---|---|
| 谁 | `turn/*`、`step/*`、`system/message`、`user/message`、`assistant/message`、`assistant/attempt`、`tool/*` | `agent/*`、`tools/*`、`fs/*`、`telemetry/*`、`llm/stream` |
| 去处 | 追加进会话日志，重启后可重建 | 只在运行期协调，进程结束就没了 |
| 谁消费 | transcript、fork、恢复、遥测、持久化 | 队列与状态、提示词拦截、取消、错误处理 |
| 广播口 | `session/event`（提交后 emit） | 各自的事件域 |

`agent/assistant-stream` 属于第二列，发布进程本地 start、瞬态 chunk 与 end frame。loop 会在提交的 end frame 之前，把完整紧凑 stream 提交为一个 message 或仅日志 attempt。进程在 settlement 前硬中断，**不会留下持久 attempt stream**。

`turn/*`、`step/*`、`tool/call`、`tool/result`、`compaction/*` 是持久会话事件类型，**不是同名 Cordis 事件**：要观察它们就监听 `session/event` 看 `event.type`。01 §6.4 已经点出这一条，这里补上它为什么是这样。

`agent/pre-step`、`agent/request`、`llm/stream` 和三个 `tools/*` 事件是 waterfall 的，监听器必须调 `next()` 才委托下去；`agent/turn-stopping` 是 serial 且没有 `next()`。

> 来源：`docs/architecture.zh.md`「轮次流程」与「事件」；`docs/agent-lifecycle.zh.md` 的时序图。

## 7. seam：换一个 provider 就换掉整个产品

一条 seam 是一项可替换能力，三个角色分工：声明接口的 **Service Definition**、实现它的 **Service Provider**、使用它的 **Consumer**（通常是面向模型的工具）。一个包可以同时承担多个角色，但单一角色本身不是 seam。

添加一项能力意味着把三者一并设计。反过来说，这也解释了 DSH 为什么看起来「什么都能换」：因为替换点不在工具里，在服务上。

一个具体后果：文件系统与进程提供方共享同一个执行世界，所以把它们指向远程沙箱，Bash、PTY 和 LSP 就一起搬了过去，不需要任何提供方专用分支。官方「新行为的归属位置」表就是这张 seam 清单的索引，其中与本节直接相关的几条：

| 目标 | 机制 |
|---|---|
| 添加模型提供方 | 在 `ctx.llm` 上注册适配器 |
| 添加 shell 执行 | 注册 `ctx.shell` 后端；本地后端通过 `ctx.subprocess` spawn 进程 |
| 限制所启动的进程 | 使用 `ctx.sandbox` 后端；消费方在启动进程前包装 argv |
| 添加后台工作 | 在 `ctx.jobs` 上注册 |
| 添加用户命令 | 在 `ctx.commands` 上注册，无需模型轮次 |
| 添加模型可见上下文 | 调 `agent.inject()`，落到下一次获准的请求 |

01 §4.4 那句「不要把部署策略写进工具里」是这条原则的一个实例。完整的 seam 图见官方 `docs/capability-seams.zh.md`。

## 8. 工具执行的完整流水线

01 §4.4 列了五个扩展点。它们在一次调用里的先后与彼此的关系，官方给了流程图：

```text
model → tool/call（执行前就落日志）→ UI 调用态卡片
      → tools/pre-execute（waterfall：钩子、权限、沙箱）
      → 已注册的单调守卫（deny 或弃权；身份受保护）
      → ctx.approval（一次性询问；缺席或无法回答即拒绝）
      → tools/execute（waterfall：超时、重试、指标，环绕分发）
      → 工具 execute() 本体 → fs/write-intent 或 fs/edit-intent（仅工具侧文件变更）
      → tools/post-execute（waterfall：接受、阻断、替换、附加上下文）
      → 注册表外层规范化（流水线/结果快照抛错转为 isError）
      → ToolDefinition.finalizeContent（最后一道只限内容的不变式）
      → tools/result（同步通知，冻结的权威结果）
      → tool/result（会话事件：唯一面向模型的结果）
      → UI 完成态卡片
```

三处在 01 里看不出来的：

- **`tools/pre-execute` 先跑，单调守卫在它之后。** 审批发生在守卫之前（`pre` 返回 `ask` 时走 `ctx.approval`），而不得重新排序的所有者策略注册为守卫。
- **注册表对候选结果做无损快照**，快照失败就先规范化，之后由已被快照固定的 `finalizeContent` 强制执行同步、仅限内容的不变式。这样钩子才能跨不同工具系列，而不用把工具和某个策略服务耦合。
- **`additionalContexts` 是在已记录的工具结果之后**作为 `user/message` 注入的，FIFO。

> 来源：`docs/tool-execution-pipeline.zh.md`。
