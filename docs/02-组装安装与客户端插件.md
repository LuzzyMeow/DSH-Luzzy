# 02 · 组装、安装与客户端插件

## 1. 运行中的 dsh 是一棵插件树

启动时的 `dsh` 由若干层按序叠加而成，后应用的层按行胜出。

### 1.1 层顺序

在空根之上依次应用：

1. profile 的 `dsh.profile.bundles` 列表所列的各个组合包 patch，按列表顺序
2. profile 自己的 `cordis.patch.yml`
3. home 级的 `$DSH_HOME/cordis.patch.yml`（各 profile 共享的机器本地偏好）
4. 每个 `--patch <path>` overlay，按 argv 顺序

应用参数不是另一层 patch。

### 1.2 本机实测的层结构

在这台机器上跑 `dsh --profile desktop --dump-config`，输出 586 行，层标记逐段可见：

```
# == @deepseek-ai/dsh-base
# == @deepseek-ai/dsh-base, patched by @deepseek-ai/dsh-web-app
...
# == @deepseek-ai/dsh-web-app
# == dshmarket
# == dsh-smooth-stream
# == dsh-thoughtdag
# == C:\Users\Administrator\.dsh\profiles\desktop\cordis.patch.yml
```

顺序与官方描述的层顺序一致：先 base，再被 web-app 打补丁，然后是三个第三方组合包，最后是用户自己的 patch 层。

### 1.3 profile 与组合包的区别

两个概念都由一份 `package.json` 描述，但 `dsh` 键下携带的 manifest 种类不同。

| | 组合包（bundle） | profile |
|---|---|---|
| 回答的问题 | 这个包贡献什么？ | 这套配置由哪些组合包按什么顺序组成？ |
| manifest | `dsh.bundle` | `dsh.profile` |
| 位置 | 一个 npm 包 | `$DSH_HOME/profiles/<name>` 目录 |
| 谁写 | 你编写并分发 | 用户用 `dsh --profile <name>` 启动 |

**没有东西同时是两者。**

### 1.4 本机实测：一个真实 profile

`~/.dsh/profiles/desktop/package.json` 的内容：

```json
{
  "name": "dsh-profile-desktop",
  "private": true,
  "dependencies": {
    "dsh-smooth-stream": "0.6.1",
    "dsh-thoughtdag": "0.4.15",
    "dshmarket": "1.47.0"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dshmarket",
        "dsh-smooth-stream",
        "dsh-thoughtdag"
      ],
      "patchReload": "live"
    }
  }
}
```

目录里同时躺着：`cordis.patch.yml`（用户自己的 patch 层）、`cordis.yml`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`.npmrc`、`node_modules/`，以及若干 `.bak-*` 备份文件。

官方文档说 profile manifest「从不需要手写」：`dsh --profile <name> --from-default-profile <template>` 可以从随附模板创建，`dsh plugin` 则维护其中已安装的 bundle 列表。

## 2. 三条挂载路径

| 路径 | 适用场景 | 做法 |
|---|---|---|
| **外置插件**（多数场景的推荐） | 自研、不开源、单独发布 | 独立 npm 包；profile 里用 `dsh plugin add` 安装；`package.json` 声明 `dsh.bundle` 后自动进入 bundle 层 |
| **临时 overlay** | 调试、演示 | `dsh --profile <name> --patch ./overlay.yml` |
| **仓库内包** | 给 DSH 本身贡献代码 | 放到 `packages/<group>/<pkg>/`，见官方 `docs/cookbook/adding-a-package.md` |

## 3. 打包成可安装的组合包

### 3.1 目录结构

```
hello-plugin/
├── package.json       # 声明 dsh.bundle
├── cordis.patch.yml   # profile 列出该 bundle 时应用的层
└── index.js           # patch 行引用的插件模块
```

### 3.2 package.json

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": {
    "bundle": {
      "patch": "./cordis.patch.yml"
    }
  }
}
```

### 3.3 cordis.patch.yml

与你写过的 `--patch` overlay 一样，是一个 patch 条目的 YAML 数组。区别在于：**插件行按包名引用，而不是相对源码路径**，这样 Node 的模块解析才能找到已安装的代码。

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin
```

对照本机实测的真实插件 `~/.dsh/plugins/dsh-tabbit-plugin/cordis.patch.yml`：

```yaml
- insert:
    - id: tabbit
      name: '@tabbit-ai/dsh-tabbit'
```

### 3.4 没有 dsh.bundle 的包

仍然可以安装，但只作为普通依赖：`dsh plugin` 会打印警告，且不激活任何层。如果一个库是供插件包 import 而不是供用户启用的，就用这种格式。

## 4. 安装到 profile

```sh
dsh plugin --profile demo add ./hello-plugin
```

`dsh plugin` 在 profile 目录内转发给 pnpm，所有 pnpm 子命令都可用。

首次使用会初始化 profile（`@deepseek-ai/dsh-base` 作为第一个组合包），pnpm 链接该 checkout，而 `dsh` 因为包声明了 `dsh.bundle`，把它追加进 `dsh.profile.bundles`：

```json
{
  "name": "dsh-profile-demo",
  "private": true,
  "dependencies": { "dsh-hello-plugin": "link:/path/to/hello-plugin" },
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "dsh-hello-plugin"] } }
}
```

**先验证再启动**：

```sh
dsh --profile demo --dump-config    # 应显示 "# == dsh-hello-plugin" 层
dsh --profile demo
```

卸载会同时移除依赖和对应的层：

```sh
dsh plugin --profile demo remove dsh-hello-plugin
```

**本机实测的 CLI 行为**：`dsh --help` 显示 `plugin` 子命令的说明是「manage a profile's plugins by forwarding the remaining arguments to pnpm in the profile directory」，与官方描述一致。`dsh plugin --help` 直接打印 pnpm 自身的帮助（本机 pnpm 11.8.0），证实了转发语义。

## 5. patch 语义（最容易踩的一处）

**后应用的层按行胜出，且 patch 会替换目标行的整个 `config` 值，而不是深度合并各键。**

这给组合包作者带来两个推论：

1. 你的 patch 可以按 `id` 覆盖前面各层的行，**但必须重述该行需要的每一个键**，而不是只写改动的那个。
2. 用户可以在自己 profile 的 `cordis.patch.yml` 中覆盖你的行，无需改动你的包。所以优先给出用户大概率会保留的配置默认值，其余交给 schema 承担。

**内置组合包名称始终从 dsh 安装目录解析**，pnpm 只管理树外的包。所以你的组合包可以放心依赖 `@deepseek-ai/dsh-base` 存在且与安装保持一致。

## 6. 从 GitHub 安装：构建脚本这道坎

```sh
dsh plugin --profile demo add github:you/hello-plugin
```

git 安装拉取的是**源码，不是构建产物**。没有任何环节运行你的 `build` 脚本，所以 TypeScript 包到手时没有 `lib/` 输出，加载会失败。两边各要做一件事：

**作者**提供一个 `prepare` 脚本（pnpm 在 git 安装后运行它），从源码构建出发布入口，且必须自包含：不能假设旁边有一份 monorepo checkout。

**用户**为构建授权。pnpm ≥10 在得到显式允许前拒绝运行 git 依赖的 `prepare` 脚本，所以第一次 `add` 会失败。按 pnpm 打印的包键，复制进该 profile 的 `pnpm-workspace.yaml`：

```yaml
allowBuilds:
  dsh-hello-plugin: true
```

然后重新执行 `add`。

> **把这看成「允许该包的代码在安装时于你的机器上执行」，且不在 agent 运行的任何沙箱之内。** 只对源码可信的包授权，并锁定 commit（`github:you/hello-plugin#<sha>`），让后续推送无法悄悄改变实际运行的内容。

**不想让用户做这个授权**，就改为分发构建产物，两种形式都不需要构建权限：

- **发布到 npm**，`pnpm publish` 时构建好 `lib/`；`dsh plugin add your-package` 装的就是预构建代码。
- **交付 tarball**：`pnpm pack` 打包；用户执行 `dsh plugin add ./hello-plugin-0.1.0.tgz`。

### 6.1 本机实测：allowBuilds 的真实写法

`~/.dsh/profiles/desktop/pnpm-workspace.yaml`：

```yaml
packages:
  - .

nodeLinker: hoisted
autoInstallPeers: false
allowBuilds:
  node-pty: true
```

## 7. 客户端（Web UI）插件

浏览器侧插件是另一套机制，入口在 `package.json` 的 `dsh.client`。

### 7.1 manifest 声明

以本机实测的 `dsh-thoughtdag@0.4.15` 为例：

```json
{
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "immediately": false,
      "inject": [
        "@deepseek-ai/dsh-client-modules",
        "@deepseek-ai/dsh-api-session-controller",
        "@deepseek-ai/dsh-client-connection",
        "@deepseek-ai/dsh-client-ui-conversation"
      ]
    },
    "compatibility": {
      "dshReleases": {
        "0.1.2-rc.1": "compatible",
        "0.1.5-rc.1": "compatible"
      }
    }
  }
}
```

一个包通过声明 `dsh.client`（`platform: 'web'`，可选 `inject` 边、可选 `immediately`）并在 `exports["./client"]` 导出构建后的 bundle 来加入客户端插件表。

### 7.2 插槽（slots）

Slots 是 Web Client 的类型化 React 组合系统。**功能插件通过 `ctx.slots.register()` 贡献 UI，永远不 import 另一个功能插件的组件。**

```tsx
import type { Context } from '@deepseek-ai/cordis'
import type { PropsRuntime } from '@deepseek-ai/dsh-client-ui-slots'

type HeaderActionProps = PropsRuntime<'conversation.session.header.actions'>

function HeaderAction({ useSession }: HeaderActionProps) {
  const running = useSession(snapshot => snapshot.running)
  return <button disabled={running}>Review</button>
}

export const inject = ['slots']

export function apply(ctx: Context): void {
  ctx.slots.inject('conversation.session.header.actions', () =>
    ctx.slots.register({
      name: 'conversation.session.header.actions',
      id: 'review',
      order: 100,
    }, HeaderAction))
}
```

**为什么用 `ctx.slots.inject()`**：注册和声明都遵循 Cordis effect 生命周期。释放一个 entry 会移除它的贡献，并递归折叠它声明的子插槽。往别人的插槽里贡献的功能必须用 `inject(key, callback)`：回调在每个声明生命周期运行一次，owner 折叠时它的 effect 被移除，owner 重新挂载时再跑一次。

**注册到未声明的插槽、或声明一个已被别处拥有的子插槽，会在插件激活期间失败。**

### 7.3 基数与作用域

| 轴 | 值 | 含义 |
|---|---|---|
| 基数 | `single` | 一个格子。优先级最高的渲染 |
| 基数 | `list` | 用必需 `id` 寻址，按 `order` 再按注册顺序排列 |
| 基数 | `keyed` | owner 派发 `entryKey`，匹配的格子渲染 |
| 基数 | `chain` | 每个 entry 提供纯 `select(owner)` 函数，优先级序中第一个非空结果渲染 |
| 作用域 | `root` | 一个 root 作用域的组件与 store 实例 |
| 作用域 | `session-maybe` | 跟随当前选择，但没有 Session 时仍可渲染 |
| 作用域 | `session` | 要求已解析的 Session 绑定 |

`priority` 是 `single` / `list` / `keyed` 的遮蔽等级，也是 `chain` 的选举顺序，**值越小越先运行或渲染**。

**普通追加型贡献应该选一个新的 list `id` 或 keyed `key`；故意复用已发布的格子就是替换它的呈现。**

### 7.4 真实客户端插件解剖

本机实测 `~/.dsh/plugins/dsh-tabbit-plugin/lib/client.js`（Tabbit Browser 随附的 DSH 集成插件）。它做的事是：在侧边栏底部加一个「本地智能体」入口。

```js
window.__ModuleLoader__.load({
  id: '@tabbit-ai/dsh-tabbit',
  factory: (require) => {
    const module = { exports: {} }
    const exports = module.exports
    const { jsx, jsxs } = require('react/jsx-runtime')
    const { IconAgentPresetOutline16, Tooltip } =
      require('@deepseek-ai/dsh-client-ui-primitives')

    // 注入 CSS，用 data 属性去重
    if (document.querySelector('style[data-plugin-css="@tabbit-ai/dsh-tabbit"]') === null) {
      const style = document.createElement('style')
      style.dataset.pluginCss = '@tabbit-ai/dsh-tabbit'
      style.textContent = css
      document.head.appendChild(style)
    }

    const NS = 'tabbit'
    const zh = { 'localAgent.open': '本地智能体' }
    const en = { 'localAgent.open': 'Local Agents' }
    const inject = ['slots', 'locale']

    function apply(ctx) {
      ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'tabbit: dictionaries')
      ctx.slots.inject('sidebar.footer.action', () => ctx.slots.register({
        name: 'sidebar.footer.action',
        id: 'tabbit-local-agent',
        order: 100,
        locale: NS,
      }, LocalAgentAction))
    }

    exports.apply = apply
    exports.inject = inject
    return module.exports
  },
})
```

值得注意的几点：

- **宿主侧是空的**：同目录的 `lib/index.js` 全文只有两行，即注释 `/** Browser-only Tabbit integration. */` 和 `export function apply() {}`。纯客户端插件在宿主侧留一个空 `apply` 是合法的。
- **客户端 bundle 用 `window.__ModuleLoader__.load()` 注册**，factory 接收一个 `require`，内部用裸 `require` 拿 React 运行时和 UI 基础组件。
- **CSS 用 `data-plugin-css` 属性去重**，避免重复注入。
- **国际化走 `ctx.locale.register(NS, { zh, en })`**，注册在 `ctx.effect()` 里，卸载时自动撤销。
- **插槽注册的 `locale` 字段**让组件拿到 `t` 函数（组件里用 `t('localAgent.open')`）。
- **CSS 变量用 `--dsw-alias-*`**（如 `--dsw-alias-label-primary`、`--dsw-alias-interactive-bg-hover`）跟随主题。

### 7.5 插槽层级（节选）

官方文档给出的完整声明树中，常用的几个位置：

```
root
├─ sidebar
│  ├─ sidebar.brand.mark
│  ├─ sidebar.brand.name
│  ├─ sidebar.footer.action          ← Tabbit 插件用这个
│  └─ sidebar.settings
│     ├─ settings.section
│     │  ├─ settings.general.item
│     │  ├─ settings.models.provider-card
│     │  └─ settings.plugins.tab
│     │     └─ settings.plugin.item
├─ main
│  └─ main.conversation
│     ├─ conversation.session.header
│     │  ├─ conversation.session.header.actions
│     │  ├─ conversation.session.header.utilities
│     │  └─ conversation.session.header.corner
│     ├─ conversation.composer.bar
│     │  ├─ conversation.input.attachments
│     │  ├─ conversation.input.permission
│     │  ├─ conversation.input.plan
│     │  └─ conversation.input.model
│     └─ conversation.chat.node
│        ├─ conversation.chat.assistant-actions
│        └─ tool.call.toolview        ← 工具 UI 卡片
├─ rightbar
│  └─ rightbar.session
│     └─ sidebar.right.pane.tab
└─ shell.overlay
```

**一个子插槽只在具名 parent entry 挂载期间存在**，所以可选的功能 entry 可以让整个子树作为一个生命周期单元出现或消失。

`root` 是唯一的内建声明，也是唯一通过 Cordis 服务本身渲染的 key。

### 7.6 扩展规则

- 导入另一个功能包**只用 `import type`** 拿声明；永远不要 import 或 re-export 它的运行时值。
- **新的子插槽只在拥有并渲染该位置的组件里声明。** 其他包用 `ctx.slots.inject()` 等待，通过 `ctx.slots.register()` 贡献。
- 业务与传输状态留在各自拥有的 Cordis 服务或 Client model 里。**Slot store 只放共享的查看与交互状态。**
- 在变更之间保持 observable source 和 snapshot 身份的稳定。
- 在 UI 域之间传 JSON 兼容的数据和回调。`hooks` 隔间是裸 observable 的唯一例外；React 内容走插槽传递。
- **把 `single` 和已占用的 keyed 格子当作替换点。** 追加型扩展用 list id 或未被占用的 key。

### 7.7 工具如何拿到专属 Web 卡片

内建 Web Client **不消费** `presentCall` / `presentResult`。Session 的 `page` 和 `follow` 传输原始的 `tool/call` 和 `tool/result` 事件，包括持久化的 `result.meta`。

客户端插件要把 wire 工具名注册进 `tool.call.toolview` 这个 keyed 插槽，并从 `ToolCallBlock` 的参数、内容、错误、元数据、已有的 PTC dispatch `parentCallId` 和 Session 路径事实推导组件 props。它要在本地校验这些 wire 值，对畸形或不支持的输入返回通用行。

需要让已有 Web 卡片拿到模型内容无法无损保存的有界结构化结果事实时，用 `output.presentationMeta(args, value)`。

**不要**把 React props 或选中的卡片存进 metadata，不要把宿主工具实现 import 进浏览器 bundle，也不要再建一个客户端呈现注册表。
