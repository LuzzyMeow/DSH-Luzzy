# 03 · 注意事项与来源核验

## 1. 踩坑清单

### 1.1 组装与配置类

| 现象 | 原因 | 处理 |
|---|---|---|
| 插件没生效 | 模块解析失败只记日志不崩溃，启动早期可能丢失；或 `name` 拼写有误 | 用 `dsh --profile <name> --dump-config` 确认真实组合树里有没有它 |
| 新配置项没效果 | **patch 按 id 替换整个 `config`，不是深合并** | 检查覆盖时是否丢了其他字段 |
| `!!js` 报错 | `!!js` 只允许出现在插件的 `config` 和条目的 `disabled` 下 | 其他位置改用 overlay |
| 改了一个 bundle 的配置，另一个 profile 也变了 | home 级 `$DSH_HOME/cordis.patch.yml` 是所有 profile 共享的 | 只改 profile 自己的 `cordis.patch.yml` |
| `apply` 抛异常 | 插件加载失败会明确终止进程 | 这是设计如此，不会静默跳过 |
| `dsh plugin add` 构建失败 | pnpm ≥10 需要显式允许 git 依赖的 `prepare` 脚本 | 把 pnpm 提示的包键复制进 profile 的 `pnpm-workspace.yaml` 的 `allowBuilds` |

### 1.2 生命周期类

| 现象 | 原因 | 处理 |
|---|---|---|
| HMR 热重载后残留注册 | 在 `apply` 里裸干的副作用不会被回滚 | 一切注册走 `ctx.effect()` / `ctx.on()` 系 |
| 卸载时资源泄漏 | 有需要手动清理的资源没登记 | 用 `ctx.effect(() => cleanup)` 返回处置器 |
| 清理顺序错乱 | **处置器按注册顺序逆序开始调用，但多个异步处置器并发执行，不保证逐个完成** | 有顺序依赖的清理步骤放进同一个 `ctx.effect()` 返回的处置器里，由它串行等待 |
| 服务提供方被替换后插件调用了不存在的服务 | — | 声明 `inject`，框架会自动 dispose 并在服务恢复后重新加载 |

### 1.3 事件类

| 现象 | 原因 | 处理 |
|---|---|---|
| 整条链被意外截断 | **waterfall 监听器不调 `next()` 就短路了流水线**，这是故意的设计 | 只做标注或观察的监听器必须调用 `next()` 委托下去 |
| 监听 `tool/result` 没反应 | 它可能是**持久会话事件类型**，不是同名 Cordis 事件 | 监听 `session/event` 并检查 `event.type` |
| 事件类型推不出来 | 没有声明合并 | 用 `declare module '@deepseek-ai/cordis' { interface Events { ... } }` 注册事件名 |

### 1.4 工具类

| 现象 | 原因 | 处理 |
|---|---|---|
| 模型看不到我的工具 | 工具 schema 会自动进 prompt，但 scope（预设隔离）或 `ctx.tools.restrict()` 可能把它滤掉了 | 检查 agent preset 的隔离设置与工具限制 |
| 想热换工具却出问题 | 注册借用的是只读 definition | 释放它所属的 effect，再注册替代品 |
| 卡片在回放时崩溃 | 呈现函数不是纯函数 | `presentCall` / `presentResult` 必须是 `args`（加结果）的纯函数：无 I/O、不读会话状态、不用时钟和随机数 |
| 工具没写 UI 卡片 | 有通用回退 | 没有 UI 呈现的工具回退到通用卡片（标题 = 工具名，原始参数作输入） |

### 1.5 客户端插件类

| 现象 | 原因 | 处理 |
|---|---|---|
| 插件激活就失败 | **注册到未声明的插槽，或声明一个已被别处拥有的子插槽** | 只用官方插槽层级里已存在的 key；新增子插槽要在拥有该渲染位置的组件里声明 |
| 覆盖了别人的 UI | `single` 和已占用的 keyed 格子是替换点 | 追加型扩展用新的 list `id` 或未被占用的 key |
| 客户端 bundle 加载失败 | 打包时漏了 `exports["./client"]` | 包必须声明 `dsh.client`（`platform: 'web'`）并导出构建后的 bundle |
| 启动时报一堆错 | 激活扫描时畸形声明会聚合成一个 `AggregateError` | 这是 fail-loud 设计，按报错逐个修 |

### 1.6 命名类（官方 `adding-a-package.zh.md` 有完整词表）

官方对 `ctx` key 和类名有明确约定，容易踩的几条：

- **名称必须描述当前稳定职责**，不要用首个实现、可能的未来扩展或 Cordis 基类命名。
- **单数 `ctx` key** 对应 engine / runtime / policy / controller / resolver / store 这类当前配置单一的服务；**复数 key** 对应 registry 或拥有多个具名成员的服务。
- **类的角色与 key 的单复数必须一致。**
- **不得让不兼容的 host 与 client 声明复用同一个 Cordis `Context` key。** 即使二者用独立的运行时 context，TypeScript 声明合并仍会同时看到两种类型。
- 不要只因为类继承了 Cordis `Service` 就用 `Service` 命名。

### 1.7 一条易被误引的第三方断言

第三方教程提到「function 插件必须命名导出，不要配默认导出，混合两种形式会让 Loader 丢掉 `inject` 元数据」。

这条**未在官方文档中找到直接对应段落**。官方文档给出的三种形态里，对象形式恰恰用的是默认导出。采信度：中。实践上按官方示例走即可：函数形式用命名导出，对象和类形式用默认导出。

### 2.1 插件作者视角的三条硬红线

1. **`prepare` 脚本等于在用户机器上执行代码。** 官方原文：把 allowBuilds 授权「视为允许该包的代码在安装时于你的机器上执行，且不在 agent 运行的任何沙箱之内。只对源码可信的包授权，并锁定 commit」。
2. **优先给用户留覆盖空间。** 用户可以在自己 profile 的 `cordis.patch.yml` 中覆盖你的行，无需改动你的包。给出用户大概率会保留的配置默认值，其余交给 schema 承担。
3. **不要在配置里硬编码机密。** 见下节。

### 2.2 本机观察：凭据落盘方式

本机 `~/.dsh/profiles/desktop/cordis.patch.yml` 里，MCP 服务器的凭据是以**明文**写在 `config` 下的：

```yaml
- id: mcp-anysearch
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    headers:
      Authorization: 'Bearer ${ANYSEARCH_API_KEY}'      # 本机实际是明文
- id: mcp-memos
  name: '@deepseek-ai/dsh-mcp-client'
  config:
    env:
      MEMOS_API_KEY: '${MEMOS_API_KEY}'                 # 本机实际是明文
```

（上面用占位符替换了实际值。）

**事实**：DSH 的 patch 层是本地文件，官方文档没有为 MCP 客户端配置提供环境变量引用的官方说明段落。

**建议**（未在官方文档中核实，属工程惯例）：凭据文件加进 `.gitignore`，不要把 profile 目录纳入版本控制；需要共享 profile 时，先替换掉 `config` 里的凭据字段。

**本机现状提醒**：`~/.dsh/profiles/desktop/` 下有多个 `*.bak-*` 备份文件（`package.json.bak-tabbit-20260909-172348`、`pnpm-lock.yaml.bak-tabbit-20260909-172349` 等），以及 `settings.yaml.bak-*` 系列。备份是好习惯，但备份文件同样包含凭据，清理时注意一并处理。

## 3. 版本兼容

**DSH 处于 developer preview**，官方 README 明确写道：

> DeepSeek Harness is in *developer preview* and iterating rapidly. **THERE WILL BE COMPATIBILITY-BREAKING CHANGES.**

本机实测：`dsh --version` 输出 `0.1.5-rc.1`。

一个可参考的实践：本机安装的 `dsh-thoughtdag@0.4.15` 在自己的 `package.json` 里声明了兼容矩阵：

```json
"compatibility": {
  "dshReleases": {
    "0.1.2-rc.1": "compatible",
    "0.1.5-rc.1": "compatible"
  }
}
```

这是插件作者应对快速迭代的一种做法。**注意：这个字段未出现在官方文档的 manifest 说明中**，可能是插件市场（本机 profile 里装了 `dshmarket@1.47.0`）自己的约定，采信度：中。官方文档描述的 bundle manifest 只有 `dsh.bundle` 和 `dsh.profile` 两种。

**升级后建议**：用 `dsh --profile <name> --dump-config` 重新核对组合树，确认你的层还在、config 没被别的层覆盖。

## 5. 一份最小可跑的清单

按官方「第一个插件」教程，最短路径是：

```sh
# 在仓库检出根目录
mkdir -p scratch-plugin/src
```

创建 `scratch-plugin/src/my-plugin.ts`：

```ts
import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello-plugin'

export function apply(ctx: Context) {
  console.log('[hello-plugin] plugin loaded!')
}
```

创建 `scratch-plugin/cordis.yml`（把路径替换成 `pwd` 的真实输出，**插件路径必须是绝对路径**）：

```yaml
- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'
```

启动：

```sh
pnpm dsh web --patch ./scratch-plugin/cordis.yml
```

终端应打印 `[hello-plugin] plugin loaded!`。

注意官方提示：**patch 文件只贡献配置，不会改变 loader 解析模块路径时使用的 profile 目录。**

本机（Desktop 版）对应的启动器命令不同，用 `dsh` 而非 `pnpm dsh`。
